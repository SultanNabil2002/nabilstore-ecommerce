### TAHAP 3: Pertarungan Satpam (`@ModerateThrottle()`)

*Request* melangkah masuk dan langsung dihadang oleh mesin keamanan pertama: **Throttler (Rate Limiting)**.

Di atas fungsi `create()`, Anda menempelkan stempel ini:

```typescript
    @ModerateThrottle()

```

Mari kita bedah secara presisi apa yang terjadi di dalam RAM *server* Anda pada sepersekian milidetik ini.

#### 1. Pembacaan Metadata

Mesin NestJS melihat *Request* datang dari IP Address `192.168.1.10`. Sebelum membiarkan *Request* ini masuk ke *Guard*, mesin mengecek apakah ada aturan batas kecepatan (Throttle) di rute `POST /orders` ini.

#### 2. Konflik Aturan (Global vs Lokal)

* **Hukum Global (`AppModule`):** Mesin ingat bahwa di `app.module.ts` ada aturan global: `ttl: 60000, limit: 10`. (Maksimal 10 *request* per 60 detik).
* **Hukum Lokal (`OrdersController`):** Namun, mesin melihat stempel `@ModerateThrottle()` tertempel khusus di rute ini. Di dalam file `custom-throttler.decorator.ts`, stempel ini berisi aturan: `ttl: 1000, limit: 5`. (Maksimal 5 *request* per 1 detik).

**Logika Override (Penimpaan):**
Dalam arsitektur NestJS, aturan yang paling spesifik (yang menempel langsung di fungsi) akan **selalu menang** melawan aturan global. Mesin secara otomatis membuang aturan 60 detik tadi ke tempat sampah (hanya untuk rute ini), dan murni menerapkan aturan 1 detik.

#### 3. Eksekusi Pencatatan di Memori (Buku Tamu Satpam)

Satpam Throttler mencatat IP Address si pengirim ke dalam memorinya.

**Wujud Buku Tamu Throttler di Memori:**

```json
{
  "192.168.1.10_POST_orders": {
    "totalHits": 1,
    "expiresAt": "1718000001000" // (Waktu saat ini + 1000 milidetik)
  }
}

```

* Karena `totalHits` masih **1** (jauh di bawah limit **5**), Satpam Throttler memberikan lampu hijau.
* *Request* diizinkan lewat!

*(Catatan Skenario: Seandainya user ini menggunakan bot dan menembak rute ini 6 kali dalam waktu setengah detik, nilai `totalHits` akan menjadi 6. Satpam Throttler akan memblokirnya secara instan, merubah Request tersebut menjadi Error `429 Too Many Requests`, dan Request itu tidak akan pernah sampai ke tahap Guard maupun Service).*

---

Sampai di titik ini, paket *Request* kita terbukti dikirim oleh manusia normal (bukan *spammer*), lolos dari Satpam Throttler, dan siap berhadapan dengan barisan pertahanan berikutnya.

### TAHAP 1: Peta Navigasi (Bagaimana Request Mencapai `JwtAuthGuard`?)

Sebelum kita membedah isi *Guard*, kita harus tahu bagaimana aliran listriknya bisa sampai ke sana.

2. Mesin Router NestJS mendeteksi bahwa URL tersebut mengarah ke class `OrdersController`.

### TAHAP 2: Membedah Anatomi `JwtAuthGuard` Secara Intim

Mesin sekarang berada di dalam file `src/common/guards/jwt-auth.guard.ts`.

```typescript
@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
    constructor(private reflector: Reflector) {
        super();
    }

    canActivate(context: ExecutionContext) {
        return super.canActivate(context);
    }
}

```

#### 1. Misteri Variabel `reflector: Reflector`

Anda bertanya, *mana contoh isinya?*
`Reflector` bukanlah objek penyimpan data statis, melainkan sebuah **Alat Pemindai (Scanner Utility Class)** bawaan inti NestJS (`@nestjs/core`). Saat disuntikkan ke dalam `constructor`, wujudnya di dalam RAM komputer Anda adalah kumpulan fungsi (metode) untuk membaca Metadata/Stempel.

**Wujud Visual `reflector` di Memori:**

```json
{
  "getAllAndOverride": [Function: getAllAndOverride],
  "getAllAndMerge": [Function: getAllAndMerge],
  "get": [Function: get],
  "getAll": [Function: getAll]
}

```

*(Catatan: Alat ini sengaja disiapkan di dalam constructor `JwtAuthGuard` ini meskipun belum dipakai di fungsi `canActivate` ini. Ini adalah persiapan arsitektur jika sewaktu-waktu Anda ingin membuat rute publik/bebas token menggunakan `@SetMetadata('isPublic', true)`).*

#### 2. Misteri `context: ExecutionContext`

Saat Router NestJS melempar Request ke dalam portal `canActivate`, ia tidak melempar Request mentah. Ia membungkusnya dalam `ExecutionContext`.

**Wujud Utuh `context` di Memori (Snapshot JSON saat eksekusi):**

```json
{
  "type": "http",
  "args": [
    { 
      "method": "POST", 
      "url": "/api/v1/orders", 
      "headers": { "authorization": "Bearer eyJhbG..." },
      "body": { "shippingAddress": "...", "items": [...] } 
    }, 
    { "statusCode": 200, "send": [Function] }, 
    [Function: next]
  ],
  "getClass": [Function: getClass],    // Jika dipanggil, me-return referensi class OrdersController
  "getHandler": [Function: getHandler], // Jika dipanggil, me-return referensi fungsi create()
  "switchToHttp": [Function: switchToHttp],
  "switchToRpc": [Function: switchToRpc],
  "switchToWs": [Function: switchToWs]
}

```

#### 3. Pembedahan `canActivate` Lokal vs `super.canActivate`

Ini adalah perbedaan yang sangat krusial:

* **`canActivate(context: ExecutionContext)`**: Ini adalah fungsi milik class `JwtAuthGuard` Anda sendiri. Ini hanyalah **Pintu Kosong**.
* **`super.canActivate(context)`**: Kata `super` adalah referensi ke class induk (yaitu `AuthGuard('jwt')` bawaan pustaka `@nestjs/passport`).

**Proses Logikanya:**
Fungsi `canActivate` milik Anda dipanggil oleh mesin NestJS. Namun, alih-alih Anda yang pusing menulis kode untuk mengecek token, fungsi Anda langsung berteriak ke class induknya: *"Hai Induk (super), tolong ambil alih context ini dan jalankan fungsi `canActivate` milikmu!"* Fungsi `canActivate` milik induk inilah yang berisi ratusan baris kode rumit untuk membekukan *Request* dan memerintahkan file `jwt.strategy.ts` untuk mulai bekerja.

### TAHAP 3: Membedah Deklarasi Induk `PassportStrategy(Strategy)`

Sebelum kita melihat proses kriptografi, kita mendarat di baris paling atas file `src/modules/auth/strategies/jwt.strategy.ts`.

```typescript
export class JwtStrategy extends PassportStrategy(Strategy) {

```

**Apa sebenarnya `PassportStrategy(Strategy)` itu?**
Di ekosistem Node.js, pustaka keamanan bernama **Passport.js** adalah standar industri, namun ia dirancang untuk mesin *Express.js*, bukan *NestJS*.

* `Strategy` (diimpor dari `passport-jwt`): Ini adalah kerangka mesin yang murni bertugas membedah token.
* `PassportStrategy(...)` (diimpor dari `@nestjs/passport`): Ini adalah **Fungsi Adaptor/Jembatan**. Ia mengambil mesin `Strategy` murni tadi, dan membungkusnya agar kompatibel dengan sistem Injeksi Dependensi (*Dependency Injection*) milik NestJS, sehingga Anda bisa menyuntikkan `PrismaService` dan `ConfigService` ke dalamnya.

### TAHAP 4: Ruang Interogasi Kriptografi (Fase Terdalam `super`)

Kita sekarang masuk ke dalam ruang mesin yang sebenarnya di dalam `constructor`.

```typescript
        super({
            jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
            ignoreExpiration: false,
            secretOrKey: configService.get<string>('JWT_SECRET') as string,
        });

```

Anda meminta proses pencocokan token secara detail absolut. Inilah yang terjadi di dalam mesin operasi Node.js saat kode `super({...})` ini memproses objek Request.

#### 1. Ekstraksi Token Mentah

Fungsi `ExtractJwt...` menyedot teks dari Header `authorization`.
*Teks Mentah:* `eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyLTEyMyIsImVtYWlsIjoicGVtYmVsaUBnbWFpbC5jb20iLCJpYXQiOjE3MTkwMDAwMDAsImV4cCI6MTcxOTAwMDkwMH0.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c`

#### 2. Proses Pembongkaran Matematika Kriptografi

Token selalu terdiri dari 3 bagian yang dipisahkan oleh titik (`.`). Mesin akan memotongnya menjadi tiga variabel:

* **Header:** `eyJhbG...` (Format Base64Url). Jika di- *decode* isinya: `{"alg": "HS256", "typ": "JWT"}`
* **Payload:** `eyJzdW...` (Format Base64Url). Jika di- *decode* isinya: Data pengguna (ID, email, waktu).
* **Signature (Tanda Tangan Asli):** `SflKxw...` (Ini adalah segel digital yang dibuat saat pengguna *Login*).

#### 3. Proses Validasi Tanda Tangan (Pencocokan)

Mesin sama sekali tidak langsung memercayai isi Payload tersebut. Jika *hacker* mengubah isi Payload, tanda tangan lama menjadi tidak valid. Bagaimana mesin mengetahuinya?

1. Mesin membaca algoritma dari Header (`"alg": "HS256"`).
2. Mesin mengambil variabel kunci rahasia Anda: `secretOrKey` (misal isinya dari `.env` adalah `"KunciRahasia2025"`).
3. Mesin di dalam *server* Anda melakukan perhitungan kriptografi mandiri menggunakan rumus:

$$\text{SignatureBaru} = \text{HMAC-SHA256}(\text{HeaderBase64} + "." + \text{PayloadBase64}, "KunciRahasia2025")$$


4. Mesin membandingkan hasil hitungannya secara presisi *byte-per-byte* dengan Tanda Tangan Asli yang dibawa oleh token:
* `Apakah SignatureBaru === SignatureAsli?`
* Jika cocok: Lolos! Mesin yakin 100% token ini dibuat oleh *server* ini dan isinya tidak pernah diubah (dimanipulasi) di tengah jalan.
* Jika beda 1 karakter saja: Eksekusi berhenti total. Mesin melempar Error 401.



#### 4. Validasi Kadaluarsa (`ignoreExpiration: false`)

Setelah lolos tanda tangan, mesin melihat isi Payload yang sudah di- *decode*. Ia mengecek properti `"exp"` (Expiration Time).

* Misal `"exp": 1719000900` (Waktu Unix).
* Mesin mengecek jam internal *server* saat ini.
* Jika waktu *server* sudah melewati angka `1719000900`, mesin melempar Error 401.

### 1. Membedah Pabrik Stempel (`roles.decorator.ts`)

File ini bertindak sebagai **Mesin Pembuat Label**. Tanpa file ini, Anda tidak akan bisa menempelkan aturan kasta di atas rute-rute sensitif (seperti rute *Update* Kategori atau *Delete* Produk).

**Kode yang Dibedah:**

```typescript
import { SetMetadata } from "@nestjs/common";
import { Role } from "@prisma/client";

export const ROLES_KEY = 'roles';
export const Roles = (...roles: Role[]) => SetMetadata(ROLES_KEY, roles);

```

**Pembedahan Baris per Baris:**

1. **`export const ROLES_KEY = 'roles';`**
Ini adalah kunci rahasia atau "Nama Variabel Internal" untuk mesin pemindai (Reflector). Anda mendeklarasikannya di sini agar di dalam `RolesGuard`, satpam tidak perlu menebak-nebak nama labelnya, melainkan tinggal memanggil `ROLES_KEY`.
2. **`export const Roles = (...roles: Role[]) =>`**
* Tanda titik tiga `...` disebut **Rest Operator** di JavaScript. Ini memungkinkan Anda memasukkan parameter tanpa batas saat memakai dekorator.
* Misalnya, Anda bisa menulis `@Roles(Role.ADMIN)` atau `@Roles(Role.ADMIN, Role.USER)` sekaligus. Mesin akan otomatis membungkus semua nilai tersebut menjadi sebuah *Array* di dalam memori.
* `Role[]` berasal dari Prisma, memastikan bahwa kasta yang diketik harus valid (hanya ada `USER` dan `ADMIN` sesuai *schema* *database* Anda).


3. **`SetMetadata(ROLES_KEY, roles)`**
Ini adalah sihir intinya dari NestJS. Fungsi ini menembakkan lem meta-data ke memori rute tersebut. Ia menempelkan *Array* `['ADMIN']` dan memberinya label `'roles'`.

Nantinya, label inilah yang diendus dan dicari oleh `this.reflector.getAllAndOverride(...)` di dalam `RolesGuard`!

### TAHAP 1: Intersepsi Parameter `@Body()`

Di dalam `orders.controller.ts`, Anda menuliskan parameter penangkap ini:

```typescript
    async create(
        @GetUser("id") userId: string,
        @Body() createOrderDto: CreateOrderDto // <--- FOKUS KITA DI SINI
    ) {

```

**Apa yang terjadi di RAM saat baris ini tersentuh?**

1. Mesin Router NestJS melihat dekorator `@Body()`.
2. Router menyedot teks JSON mentah dari HTTP Request yang dikirim oleh *Frontend*.
3. **Penting:** Router **TIDAK** langsung memasukkan JSON mentah itu ke dalam variabel `createOrderDto`.
4. Router melempar JSON mentah tersebut ke mesin cuci global bernama **ValidationPipe** (yang biasanya sudah didaftarkan di `main.ts` oleh instruktur Anda menggunakan sintaks `app.useGlobalPipes(new ValidationPipe(...))`).

**Wujud JSON Mentah (Plain Object) yang Masuk ke ValidationPipe:**

### TAHAP 2: Operasi Sihir `class-transformer` (Reinkarnasi Objek)

File JSON yang mengalir lewat internet kehilangan "roh"-nya. Ia hanyalah teks mati, bukan sebuah *Class*. Mesin `class-validator` tidak bisa memvalidasi teks mati.

Di sinilah Segitiga Emas dari file `create-order.dto.ts` Anda bekerja keras:

```typescript
    @IsArray()
    @ValidateNested({ each: true })
    @Type(() => OrderItemDto)
    items!: OrderItemDto[];

```

**Proses Transformasi Mikroskopis:**

1. Mesin melihat `@Type(() => OrderItemDto)`.
2. Mesin menyadari: *"Oh, array 'items' ini bukan sekadar kumpulan JSON mati. Saya harus merakit ulang mereka menjadi instance Class OrderItemDto betulan!"*
3. Mesin membuat perulangan (`loop`) di dalam RAM, menyalin data dari JSON mentah, dan memompanya ke dalam cetakan class `OrderItemDto`.

**Wujud Data Setelah Di-Transformasi (Instance Class):**

```javascript

  shippingAddress: 'Jl. Budi Luhur No. 99',
  items: [
    OrderItemDto { productId: 'prod-111', quantity: 2, price: 150000 },
    OrderItemDto { productId: 'prod-222', quantity: 1, price: 'DUA_RIBU' }
  ]
```

### PART 5: Membedah Sihir Ekstraksi Parameter (`get-user.decorator.ts`)

Di Part 2, Satpam `JwtAuthGuard` berhasil menyuntikkan data pembeli ke dalam objek `Request`. Masalahnya, objek `Request` itu sangat besar dan tersembunyi di balik layar. Bagaimana cara kita menyedot *hanya* ID pembelinya saja untuk dimasukkan ke parameter fungsi di *Controller*?

Di sinilah instruktur Anda membuat **Alat Penyedot Khusus (Custom Param Decorator)**.

**Kode yang Dibedah:**

```typescript
import { createParamDecorator, ExecutionContext } from "@nestjs/common";

export const GetUser = createParamDecorator((data: string | undefined, ctx: ExecutionContext) => {
    const request = ctx.switchToHttp().getRequest();
    const user = request.user;

    return data ? user?.[data] : user;
});

```

#### TAHAP 1: Pabrik Dekorator (`createParamDecorator`)

* Sama seperti `@Body()` menyedot *body* dan `@Param()` menyedot *URL*, fungsi `createParamDecorator` adalah mesin pembuat penyedot kustom bawaan NestJS.
* Mesin ini menerima fungsi panah (*arrow function*) yang memiliki dua parameter bawaan: `data` dan `ctx`.

#### TAHAP 2: Parameter `data` (Si Penerima Perintah)

Saat Anda menulis `@GetUser("id")` di *Controller*, kata `"id"` tersebut ditangkap oleh mesin dan dimasukkan ke dalam variabel `data`.

* **Wujud `data` di memori:** `"id"` (bertipe *string*).
* Jika Anda hanya menulis `@GetUser()` tanpa isi kurung, wujud `data` adalah `undefined`.

#### TAHAP 3: Membongkar Brankas (`ctx` & `request.user`)

```typescript
    const request = ctx.switchToHttp().getRequest();
    const user = request.user;

```

* Mesin menggunakan kunci pembuka `ctx.switchToHttp().getRequest()` untuk mengakses kembali HTTP Request yang sedang berjalan.
* Mesin membuka laci `request.user` (yang sebelumnya diisi oleh `JwtAuthGuard`).
* **Wujud `user` di memori saat ini:**
```json
{
  "id": "user-999-xyz",
  "email": "pembeli@gmail.com",
  "role": "USER"
}

```



#### TAHAP 4: Operasi Sintaks Tingkat Lanjut (Baris Return)

Ini adalah baris paling jenius dan padat di seluruh file ini. Instruktur Anda menggabungkan tiga fitur canggih JavaScript (Ternary, Optional Chaining, dan Bracket Notation) dalam satu baris:

```typescript
    return data ? user?.[data] : user;

```

Mari kita bedah logikanya perlahan-lahan dari kiri ke kanan:

1. **`data ?` (Ternary Operator / Logika "Apakah"):**
* Mesin bertanya: *"Apakah variabel `data` ada isinya?"*
* Karena Anda mengirim `"id"`, jawabannya adalah **YA** (*Truthy*).
* Maka, mesin akan mengeksekusi kode di sebelah kiri titik dua (`:`), yaitu `user?.[data]`.


2. **`user?.` (Optional Chaining / Anti-Crash):**
* Tanda tanya sebelum titik (`?.`) adalah sabuk pengaman.
* Mesin berkata: *"Coba cek variabel `user`. Jika isinya `undefined` (misalnya karena lupa memasang JwtAuthGuard), langsung berhenti di sini dan kembalikan `undefined`. Jangan paksakan mencari ke dalam, nanti server meledak (Crash)!"*
* Karena `user` ada isinya, mesin lanjut ke langkah berikutnya.


3. **`[data]` (Bracket Notation / Kunci Dinamis):**
* Di JavaScript, untuk mengambil properti `id` dari objek `user`, Anda bisa memakai `user.id`.
* Tapi karena kata `"id"` tersimpan di dalam variabel bernama `data`, Anda harus menggunakan kurung siku: `user[data]`. Mesin akan menerjemahkannya menjadi `user["id"]`.


4. **Hasil Akhir (Ekstraksi):**
* Mesin berhasil menarik nilai `"user-999-xyz"` dari dalam objek.



#### TAHAP 5: Pendaratan di Controller

Nilai string `"user-999-xyz"` tersebut di-*return* oleh dekorator, melesat kembali ke file `OrdersController`, dan disuntikkan secara tepat ke dalam variabel `userId`:

```typescript
    async create(
        @GetUser("id") userId: string, // <--- userId sekarang berisi "user-999-xyz"
        @Body() createOrderDto: CreateOrderDto 
    ) {
        return await this.ordersService.create(userId, createOrderDto)
    }

```

Sekarang, fungsi `create` Anda telah memiliki dua amunisi yang sangat solid, aman, dan tervalidasi 100%: ID Pembeli yang terjamin keasliannya dari JWT, dan Keranjang Belanja yang lolos mesin X-Ray. Keduanya siap dilemparkan ke dalam `ordersService.create` untuk dieksekusi di *Database* PostgreSQL!
