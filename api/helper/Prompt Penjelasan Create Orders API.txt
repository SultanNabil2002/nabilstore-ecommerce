### TAHAP 4: Mesin Kalkulator (Fungsi `reduce`)

Setelah seluruh keranjang dipastikan valid dan stoknya mencukupi, mesin keluar dari *looping* dan mengeksekusi baris kalkulasi ini:

```typescript
        const total = items.reduce(
            (sum, item) => sum + item.price * item.quantity, 0
        );

```

**Pembedahan Eksekusi Matematika (`reduce`):**
Fungsi `reduce` adalah cara elegan JavaScript untuk menghitung total dari sebuah *Array* tanpa harus membuat `for-loop` manual.

1. Angka `0` di bagian paling belakang adalah **Nilai Awal** (Dompet kosong).
2. Mesin memanggil barang pertama (`prod-111`, jumlah 2, harga 150000).
3. Mesin menjalankan rumus internal: $sum = 0 + (150000 \times 2)$. Nilai `sum` sekarang menjadi $300000$.
4. Mesin memanggil barang kedua (`prod-222`, jumlah 1, harga 50000).
5. Mesin menjalankan rumus lagi: $sum = 300000 + (50000 \times 1)$. Nilai `sum` sekarang menjadi $350000$.
6. Karena barang habis, nilai akhir dikembalikan ke dalam variabel `total`.

**Wujud Variabel di RAM:**

```javascript

```

Sekali lagi, perhatikan keamanannya: Nilai total yang akan masuk ke *Database* nanti murni merupakan **hasil perhitungan *Backend***, bukan mengambil dari nilai total karangan *Frontend*.

Kini, mesin kita telah memegang semua kunci utama: ID Pembeli, Keranjang yang valid, dan Total Harga yang akurat.

### 2. Dari Mana `sum` Mendapatkan Nilai Awal 0?

Anda bertanya: *"Bagaimana nilai awal sum bisa nol padahal tidak dideklarasikan?"*

Sebenarnya, nilai awal 0 itu **SUDAH** Anda deklarasikan secara eksplisit di dalam kode Anda! Coba perhatikan baik-baik posisi angka `0` di ujung kode ini:

```typescript
const total = items.reduce(
    (sum, item) => sum + item.price * item.quantity, 
    0  // <---- INI DIA DEKLARASINYA!
);

```

Di dalam fungsi `reduce`, parameter itu dipisahkan oleh tanda koma `,`.

* Bagian pertama adalah rumusnya: `(sum, item) => sum + item.price * item.quantity`
* Bagian kedua adalah nilai awalnya: `0`

Jika Anda menghapus angka `0` di belakang itu, mesin akan kebingungan dan mengambil data pertama dari array sebagai nilai awal, yang mana akan membuat perhitungan matematika Anda *error* parah.

### 3. Membedah Ulang Metode Array `reduce()`

Mari kita bongkar metode ini. `reduce` diciptakan untuk **mereduksi (menghancurkan/melebur)** sebuah *Array* yang tadinya berisi banyak barang, menjadi **satu nilai tunggal** (dalam kasus kita, dilebur menjadi 1 angka total harga).

Fungsi `reduce` selalu membutuhkan dua aktor utama di dalam kurungnya:
`reduce( (Akumulator, ElemenSaatIni) => ...rumus... , NilaiAwal )`

Di kode Anda, aktor tersebut diberi nama `sum` dan `item`.

* **`sum` (Akumulator/Buku Catatan Kasir):** Ini adalah variabel yang bertugas *mengingat* hasil perhitungan dari putaran sebelumnya.
* **`item` (Elemen Saat Ini/Barang di Sabuk Kasir):** Ini adalah barang yang sedang dipegang oleh kasir saat ini.

**Simulasi Gerak Lambat di Dalam Mesin Node.js:**

Ingat, keranjang (`items`) kita berisi 2 barang:
`[{ harga: 150000, jumlah: 2 }, { harga: 50000, jumlah: 1 }]`

**Detik ke-1 (Persiapan):**
Mesin melihat angka `0` di belakang. Mesin menyiapkan buku catatan (variabel `sum`), dan menulis angka **0**.

**Detik ke-2 (Putaran Pertama):**

* `item` yang dipegang = Barang pertama (harga 150000, jumlah 2).
* Mesin melihat rumus: `sum + (item.price * item.quantity)`
* Mesin menghitung: **0** + (150000 * 2) = **300.000**.
* *Sihir reduce:* Angka 300.000 ini **disimpan/ditulis ulang** ke dalam buku catatan `sum`.

**Detik ke-3 (Putaran Kedua):**

* `item` yang dipegang = Barang kedua (harga 50000, jumlah 1).
* Mesin melihat buku catatan (`sum`). Isinya sekarang bukan 0 lagi, melainkan **300.000**.
* Mesin menghitung rumus: **300000** + (50000 * 1) = **350.000**.
* Angka 350.000 disimpan ke dalam buku catatan `sum`.

**Detik ke-4 (Selesai):**
Karena array sudah habis, fungsi `reduce` berhenti bekerja. Ia mengambil angka terakhir dari buku catatan (`sum` = 350000), membuang buku catatan tersebut, dan melemparkan angka 350.000 itu ke luar untuk disimpan ke dalam variabel `const total`.

Itulah mengapa `reduce` sangat kuat. Daripada Anda harus membuat variabel `let total = 0` di luar lalu membuat `for-loop` untuk menambahkannya perlahan-lahan, `reduce` melakukan semuanya dalam satu baris kode yang elegan dan fungsional.

### 1. Tujuan Asli Looping: "Pos Satpam", Bukan "Gudang Penyimpanan"

Kesalahpahaman terbesar di sini adalah mengira bahwa *looping* `for (const item of items)` bertugas untuk **mengumpulkan** data produk agar bisa dipakai nanti saat membuat pesanan (di fungsi Prisma `$transaction`).

Padahal, **TIDAK SAMA SEKALI**.

Fungsi *looping* ini murni bertindak sebagai **Pos Satpam Pengecekan (Validasi)**.
Mari gunakan analogi Pemeriksaan Paspor di Bandara:

1. Anda menyodorkan Paspor (ID Produk).
2. Petugas (Prisma) mengecek ke komputer pusat (*Database*).
3. Setelah wajah Anda dan data di layar komputer **cocok** (Barang ada dan stok cukup), petugas mengembalikan paspor itu kepada Anda, dan melupakan data Anda dari layarnya untuk melayani penumpang berikutnya.
4. Petugas **TIDAK PERLU** menyimpan foto profil Anda di kantongnya, karena yang dia butuhkan hanyalah konfirmasi: *"Apakah orang ini sah? Ya."*

Begitu juga dengan variabel `product`. Setelah baris `if (product.stock < item.quantity)` berhasil dilewati tanpa *error*, tugas variabel `product` **SUDAH SELESAI**. Mesin tidak membutuhkannya lagi, karena data yang akan dipakai untuk menghitung total dan membuat pesanan (`productId`, `quantity`, `price`) sudah tersedia dengan lengkap di dalam array `items` bawaan *Frontend*.

### 2. Misteri `const` vs `let` di dalam Looping

Anda bertanya: *"Kenapa tidak menggunakan let?"*

Ini adalah salah satu keunikan (dan kehebatan) bahasa JavaScript modern. Di dalam struktur `for...of`, variabel yang dideklarasikan dengan `const` **tidak melanggar aturan**.

* Jika Anda menggunakan `for (let i = 0; i < 5; i++)`, Anda **WAJIB** memakai `let` karena variabel `i` terus diubah nilainya (`i = 1`, `i = 2`, dst) di dalam ruang memori yang sama.
* Tetapi pada `for (const item of items)`, setiap putaran (loop) menciptakan **ruang memori (Scope) yang benar-benar baru**.

**Visualisasi Memori Mesin:**

* **Putaran 1:** Mesin membangun "Ruangan A". Di dalam Ruangan A, mesin membuat laci permanen (`const product`). Setelah pengecekan selesai, mesin menghancurkan Ruangan A beserta isinya.
* **Putaran 2:** Mesin membangun "Ruangan B" yang baru. Di sini, mesin membuat laci permanen baru yang kebetulan namanya sama (`const product`). Karena Ruangan A sudah hancur, mesin tidak merasa ini sebagai "penimpaan" atau pelanggaran aturan `const`.

Jika Anda memakai `let product = ...` di dalam *loop*, itu tidak salah secara sintaks, tapi itu adalah *bad practice* (praktik buruk). *Programmer* senior selalu menggunakan `const` jika nilai variabel tersebut tidak pernah diubah (seperti `product = sesuatu_yang_baru`) **di dalam satu putaran yang sama**. Ini mencegah *bug* yang tidak disengaja.

### Kesimpulan

Data `product` memang sengaja dipanggil, diinterogasi (dicek stoknya), lalu dihancurkan. Ia adalah "tumbal" validasi. Mesin membuangnya demi menghemat memori RAM *server* Anda agar tidak penuh oleh data barang yang sudah tidak terpakai lagi di baris-baris bawahnya.

### TAHAP 1: Pencarian Keranjang Terakhir (`findFirst`)

Sebelum membuat struk pesanan resmi, mesin mencoba mengecek apakah pembeli ini memiliki keranjang belanja (*Cart*) yang masih menggantung.

```typescript
        const latestCart = await this.prisma.cart.findFirst({
            where: {
                userId,
                checkedOut: false,
            },
            orderBy: {
                createdAt: 'desc'
            },
        });

```

**Pembedahan Logika:**

1. **`findFirst` (Bukan `findUnique`):** Kenapa? Karena di sistem *e-commerce*, seorang *user* bisa saja membuat banyak keranjang, meninggalkannya, lalu membuat keranjang baru. `findUnique` akan *error* jika menemukan lebih dari 1 data. `findFirst` hanya akan mengambil baris paling atas.
2. **`checkedOut: false`:** Mesin menargetkan keranjang yang belum pernah dibayar.
3. **`orderBy: { createdAt: 'desc' }`:** (Descending / Menurun). Ini perintah pengurutan. Mesin menyusun keranjang dari yang paling baru dibuat ke yang paling lama. Hasil akhirnya: Mesin mendapatkan keranjang *terbaru* yang belum dibayar.

```json

  "userId": "b2f5c1d4-8a7e-4b9c-1234-abcd5678efgh",
  "checkedOut": false,
  "createdAt": "2026-06-28T12:00:00.000Z"
}

```

*(Catatan: Jika pembeli ini adalah pengguna baru dan tidak punya keranjang sama sekali di database, nilai `latestCart` ini akan menjadi `null`. Mesin tidak akan error, ia akan melanjutkan eksekusi).*

### TAHAP 2: Memasuki Gelembung `$transaction` (All or Nothing)

Ini adalah pilar paling krusial dalam sistem finansial/e-commerce. Anda mengeksekusi baris ini:

```typescript
        const order = await this.prisma.$transaction(async (tx) => {

```

**Apa itu `$transaction`?**
Bayangkan Anda sedang mentransfer uang Rp1.000.000 ke teman Anda. Di *database* bank, ada dua operasi:

1. Kurangi saldo Anda Rp1.000.000.
2. Tambah saldo teman Anda Rp1.000.000.

Apa yang terjadi jika server mati lampu / *error* tepat setelah operasi pertama sukses, tapi operasi kedua belum berjalan? Uang Anda hangus, tapi uang teman Anda tidak bertambah. Ini malapetaka!

Oleh karena itu, Prisma menciptakan gelembung `$transaction`. Aturan mutlak gelembung ini adalah **All or Nothing (Semua Berhasil, atau Batal Total)**.
Jika di dalam gelembung ini ada 100 perintah penyimpanan data, dan perintah ke-99 *error*, Prisma secara ajaib akan membatalkan ( *Rollback* ) 98 perintah sebelumnya seolah-olah tidak pernah terjadi apapun.

**Misteri Variabel `tx`:**
Di dalam gelembung ini, parameter `tx` (singkatan dari *transaction*) bertindak sebagai "Kloning" dari `this.prisma`. Di dalam gelembung ini, Anda **DIHARAMKAN** menggunakan `this.prisma`. Anda wajib menggunakan `tx`.

### TAHAP 3: Operasi Tulis Bersarang (Nested Write)

Sekarang, kita membuat pesanan di dalam gelembung tersebut. Ini adalah kode yang sangat raksasa karena melakukan banyak hal sekaligus.

```typescript
            const newOrder = await tx.order.create({
                data: {
                    userId,
                    status: OrderStatus.PENDING,
                    totalAmount: total,
                    shippingAddress,
                    cartId: latestCart?.id,
                    orderItems: {
                        create: items.map((item) => ({
                            productId: item.productId,
                            quantity: item.quantity,
                            price: item.price
                        }))
                    }
                },

```

**Pembedahan Logika Data Utama:**

* **`totalAmount: total`:** Memasukkan nilai 350.000 hasil kalkulasi mesin di Part 2. Sangat aman.
* **`cartId: latestCart?.id`:** Ini kembali menggunakan *Optional Chaining* (`?.`). Jika `latestCart` ada isinya, ambil ID-nya (`"cart-555-abc"`). Jika `latestCart` ternyata `null` (tidak punya keranjang), maka kodenya berubah menjadi `cartId: undefined`. Prisma sangat pintar, saat melihat `undefined`, ia membiarkan kolom `cartId` kosong (NULL) di PostgreSQL tanpa menimbulkan *error*.
* **`orderItems: { create: ... }`:** Ini adalah sihir **Nested Write (Tulis Bersarang)**. Anda menyuruh Prisma: *"Buatkan struk pesanan baru di tabel `Order`. TAPI TUNGGU, di waktu yang sama, tolong masukkan juga daftar barang ini ke tabel `OrderItem` dan langsung relasikan/sambungkan mereka berdua!"*

**Membedah `items.map(...)`:**
Sama seperti `reduce` adalah metode peleburan, `map` adalah metode **Penerjemahan/Fotokopi**.
Mesin mengambil array `items` bawaan *Frontend* (yang isinya cuma ID, jumlah, harga), dan mem-fotokopinya menjadi struktur baru yang dimengerti oleh tabel PostgreSQL.

### 1. Membedah Hierarki Relasi: Kenapa `product` ada di dalam `orderItems`?

Pemahaman Anda bahwa *tabel Order hanya berelasi dengan tabel OrderItem* adalah **Hampir Benar**, tapi ada satu detail penting di `schema.prisma` yang terlewat.

Sebuah tabel `Order` di sistem *e-commerce* biasanya memiliki **dua** relasi utama:

1. **Relasi ke `User`:** Siapa yang melakukan pesanan ini? (Makanya ada kolom `userId` di tabel `Order`).
2. **Relasi ke `OrderItem`:** Barang apa saja yang ada di dalam pesanan ini?

**Lalu, di mana posisi `Product`?**
Tabel `Order` **TIDAK PUNYA** relasi langsung ke tabel `Product`. Anda tidak akan menemukan kolom `productId` di dalam tabel `Order`. Mengapa? Karena satu struk pesanan bisa berisi banyak barang.

Yang berelasi langsung dengan `Product` adalah tabel `OrderItem`.
Hierarkinya (Pohon Silsilah) bentuknya seperti ini:

* **Kakek:** `User`
* **Bapak:** `Order` (Milik si Kakek)
* **Anak:** `OrderItem` (Milik si Bapak)
* **Mainan Anak:** `Product` (Milik si Anak)

**Membaca Sintaks `include` Prisma:**
Ketika kita sedang membuat `Order` (Si Bapak), dan kita menulis:

```typescript
include: {
    user: true, 
    orderItems: true
}

```

Artinya: *"Tolong panggilkan Kakeknya, dan panggilkan Anak-anaknya."* (Ini akan melakukan operasi SQL `JOIN` dan mengambil seluruh properti di tabel tersebut).

Tapi, karena *Frontend* butuh nama barang (seperti "VGA RTX 4090"), sekadar memanggil Anak (`orderItems`) tidak cukup, karena si Anak hanya tahu ID barangnya (`"prod-111"`). Kita harus menyuruh Prisma masuk lebih dalam ke saku si Anak untuk mengambil detail Mainannya:

```typescript
    orderItems: {
        include: {
            product: true // <--- "Masuk ke dalam OrderItem, lalu tarik data Product-nya!"
        }
    }

```

Itulah mengapa `product` tidak boleh ditaruh sejajar dengan `user`. Jika ditaruh sejajar, Prisma akan *error* dan berkata: *"Tabel Order tidak punya relasi ke Product! Saya tidak tahu harus JOIN ke mana!"*

### 2. Misteri DTO yang "Acak" (Benang Merahnya)

Anda bertanya: *"Apa kita ubah saja urutan baris per barisnya di order-response.dto.ts agar memudahkan saya? Apakah itu mempengaruhi kode?"*

**JAWABAN TEGAS: YA, UBAH SAJA! ITU TIDAK MEMPENGARUHI KODE SAMA SEKALI.**

Di dalam JavaScript/TypeScript, sebuah *Object* / *Class* bekerja menggunakan sistem *Key-Value Pair* (Pasangan Kunci-Nilai). Mesin komputer membaca nama kuncinya (misal: `status`, `total`), **bukan urutan barisnya**. Instruktur Anda kemungkinan besar mengetik DTO tersebut secara spontan sesuai apa yang terlintas di kepalanya, sehingga urutannya menjadi acak dan tidak rapi.

Untuk memudahkan Anda mencari Benang Merahnya, silakan ubah isi file `order-response.dto.ts` Anda agar urutannya **PERSIS** seperti urutan di `schema.prisma`.

Berikut adalah kode yang sudah saya rapikan urutannya khusus untuk Anda agar selaras dengan cara kerja Prisma:

```typescript
/* eslint-disable prettier/prettier */
//src/modules/orders/dto/order-response.dto.ts

import { ApiProperty } from "@nestjs/swagger";

export class OrderApiResponseDto<T> {
    @ApiProperty({ description: "Indicates if the request was success" })
    success!: boolean;

    @ApiProperty({ description: "Optional message", nullable: true, required: false })
    message?: string;

    @ApiProperty({ description: "Returned data", type: Object })
    data!: T;
}

// URUTAN DIRAPIKAN SESUAI SCHEMA PRISMA ORDER_ITEM
export class OrderItemResponseDto {
    @ApiProperty() id!: string;
    @ApiProperty() quantity!: number;
    @ApiProperty() price!: number;
    @ApiProperty() subtotal!: number; // (Ini tambahan komputasi backend, tidak ada di DB)
    
    // Foreign Keys / Relations
    @ApiProperty() productId!: string;
    @ApiProperty() productName!: string; // (Hasil relasi dari tabel Product)

    @ApiProperty() createdAt!: Date;
    @ApiProperty() updatedAt!: Date;
}

// URUTAN DIRAPIKAN SESUAI SCHEMA PRISMA ORDER
export class OrderResponseDto {
    @ApiProperty() id!: string;
    @ApiProperty() status!: string;
    @ApiProperty() total!: number;
    @ApiProperty() shippingAddress!: string;
    
    // Foreign Keys
    @ApiProperty() userId!: string;
    // (cartId sengaja tidak dimasukkan ke DTO karena Frontend tidak butuh data ini)

    // Relations

    items!: OrderItemResponseDto[]

    @ApiProperty() createdAt!: Date;
    @ApiProperty() updateAt!: Date;
}

```

**Konsep Benang Merah (Perbedaan Schema vs DTO):**

* **`schema.prisma` (Pola Simpan):** Aturannya kaku. Hanya berisi data mentah yang diwajibkan oleh *Database* untuk disimpan di *hard drive*.
* **DTO (Pola Tampil):** Bebas dan fleksibel. Anda bisa menambahkan data palsu hasil perhitungan (seperti `subtotal`), membuang data yang tidak penting (seperti membuang `cartId`), atau menarik data dari tabel tetangga (seperti `productName`).

### 1. Misteri `shippingAddress`: DTO Wajib vs Schema Opsional

Anda bertanya: *"Apakah instruktur salah? Apakah tidak apa-apa?"*

**Jawabannya: Instruktur Anda TIDAK SALAH, dan ini sangat TIDAK APA-APA. Bahkan, ini adalah *Best Practice* (Praktik Terbaik)!**

Mari kita bedah alasan arsitekturnya:

* **Sisi Database (Prisma - Opsional `?`):**
Tabel *Database* dirancang untuk fleksibilitas jangka panjang. Mungkin di masa depan, aplikasi Anda tidak hanya menjual barang fisik (VGA, Sepatu), tapi juga menjual **Barang Digital** (seperti *Game* Steam, *Software* VPN, atau *Course Online*). Barang digital tidak butuh alamat pengiriman. Oleh karena itu, di *Database*, kolom ini dibuat opsional (boleh `NULL`) agar sistem tidak *error* saat pesanan digital dibuat.
* **Sisi API / Frontend (DTO - Wajib `!`):**
*Frontend* (React/Next.js) paling benci dengan ketidakpastian. Jika DTO dibuat opsional, *Frontend* harus menulis kode pengecekan ekstra yang panjang seperti ini setiap kali ingin merender alamat: `if (order.shippingAddress != null && order.shippingAddress != undefined) { cetak alamat }`.

Untuk memanjakan *Frontend*, instruktur Anda memaksa DTO ini menjadi **Wajib**.

**Bagaimana cara Backend menepati janji "Wajib" ini jika di Database nilainya kosong?**
Coba Anda lihat kembali kode di dalam fungsi `map()` pada `OrdersService` yang Anda kirim sebelumnya:

```typescript
shippingAddress: order.shippingAddress ?? '',

```

Ini adalah **Sihir Operator Nullish (`??`)**. Instruktur Anda menyuruh mesin: *"Jika di Database alamatnya ada, kirimkan alamat itu. Tapi jika di Database alamatnya kosong (NULL), JANGAN kirim NULL ke Frontend. Ubah menjadi String Kosong (`''`)!"*

Berkat satu baris ini, *Frontend* selalu mendapat garansi 100% bahwa nilai `shippingAddress` pasti berwujud teks (entah teks panjang atau teks kosong), sehingga aplikasi *Frontend* tidak akan pernah *Crash/Error*.

### 2. Misteri `orderNumber` vs `id` di dalam DTO

Anda bertanya: *"Kenapa `orderNumber` tidak ada di DTO? Lalu kenapa `id` tetap ada padahal keduanya dibuat otomatis?"*

Ini murni masalah **Kebutuhan Komunikasi vs Kosmetik**.

Secara konsep, keduanya memang dibuat otomatis oleh mesin saat *checkout*, tapi fungsinya sangat berbeda:

* **Kenapa `id` (UUID) WAJIB ada di DTO?**
`id` adalah bahasa mesin. *Frontend* sangat membutuhkan `id` ini untuk melakukan tindakan selanjutnya.
Contoh: Setelah pesanan berhasil dibuat, *Frontend* ingin mengarahkan pembeli ke halaman pembayaran. *Frontend* harus memanggil rute API baru: `GET /orders/{id}/payment`. Tanpa `id` di dalam balasan pembuatan pesanan, *Frontend* akan buta dan tidak tahu pesanan mana yang harus dibayar. Oleh karena itu, `id` wajib dikirim pulang.
* **Kenapa `orderNumber` tidak ada di DTO?**
`orderNumber` biasanya hanyalah **Kosmetik Manusia** (contoh: `"INV-20260628-001"`). Ia dipakai untuk dicetak di struk PDF atau resi kurir agar mudah dibaca manusia.
Jika instruktur Anda tidak memasukkannya ke dalam `OrderResponseDto`, ada dua kemungkinan:
1. *Frontend* di halaman "*Checkout Success*" ini memang tidak mendesain UI untuk menampilkan Nomor Invoice (mungkin hanya menampikan: "Pesanan Berhasil, klik di sini untuk bayar").
2. Instruktur Anda sekadar **lupa** memasukkannya ke dalam DTO. (Ini sangat sering terjadi di dunia nyata). Jika Anda merasa *Frontend* nanti butuh menampilkan `"INV-..."`, Anda bebas menambahkannya sendiri ke DTO Anda!

Jadi, patokannya bukan *"Apakah data ini dibuat otomatis atau tidak?"*, melainkan *"Apakah Frontend membutuhkan data ini detik ini juga untuk merender layar atau melakukan aksi selanjutnya?"*

Semuanya sudah terjawab dan dibersihkan dari keraguan. Silakan ketik **"Lanjut Part 4"** jika Anda sudah siap untuk masuk ke tahap pemotongan stok dan pemformatan data raksasa!

### TAHAP 1: Misi Terakhir di Dalam Gelembung (Pemotongan Stok)

Setelah struk pesanan (`newOrder`) berhasil dicetak di *database*, kita masih berada di dalam fungsi `$transaction(async (tx) => { ... })`. Misi belum selesai. Barang sudah dibeli, berarti stok di gudang harus dikurangi!

Mesin mengeksekusi *looping* kedua ini:

```typescript
            for (const item of items) {
                await tx.product.update({
                    where: { id: item.productId },
                    data: { stock: { decrement: item.quantity } }
                })
            }

```

**Pembedahan Logika Tingkat Lanjut (Atomic Operation):**
Mengapa instruktur Anda menggunakan `{ decrement: item.quantity }`? Kenapa tidak memakai logika matematika biasa seperti `stock: product.stock - item.quantity`?

Ini adalah teknik tingkat tinggi untuk mencegah **Race Condition** (Tabrakan Data).
Bayangkan skenario ini: Stok tiket konser sisa 5. Anda dan teman Anda memencet tombol "Beli 3 tiket" di milidetik yang sama persis.

* Jika pakai logika biasa: Mesin Anda membaca stok 5, dikurangi 3 = 2. Mesin teman Anda juga membaca stok 5, dikurangi 3 = 2. Keduanya menyimpan angka 2 ke *database*. Padahal total tiket yang terjual adalah 6! *Database* Anda bocor!
* **Solusi Prisma (`decrement`):** Fitur ini mendelegasikan perhitungan matematikanya langsung ke jantung mesin PostgreSQL (disebut *Atomic Operation*). Mesin Node.js tidak perlu tahu berapa sisa stoknya. Node.js hanya berteriak ke PostgreSQL: *"Hai Database, kurangi stok barang ini sebanyak 2, lakukan di antrean internalmu dengan aman!"* PostgreSQL akan menguncinya dan memprosesnya satu per satu secara sempurna.

Semua ini dilakukan menggunakan variabel `tx` (karena kita masih di dalam gelembung). Jika salah satu produk gagal di-*update* (misalnya tiba-tiba server *database* putus koneksi), maka pembuatan `newOrder` di atas tadi akan otomatis dibatalkan (*rollback*).

### TAHAP 2: Penutupan Gelembung Transaksi

Setelah semua barang berhasil dipotong stoknya, mesin mencapai baris terakhir di dalam fungsi transaksi:

```typescript
            return newOrder;
        }) // <--- Gelembung pecah / ditutup di sini!

```

**Apa yang terjadi pada detik ini?**

1. Perintah `return newOrder;` memberi sinyal kepada Prisma: *"Semua misi di dalam gelembung telah sukses 100%!"*
2. Prisma akhirnya "Mengesahkan" (*Commit*) seluruh perubahan tersebut secara permanen ke dalam *hard drive Database*.
3. Gelembung transaksi ditutup.
4. Nilai `newOrder` yang berisi JSON raksasa nan kotor tadi kini ditangkap oleh variabel `order` yang berada di luar gelembung.

**Wujud Variabel di RAM:**

**Kenapa parameternya tidak ditulis `order: Order` saja?**

2. `user: User;`

3. `orderItems: (OrderItem & { product: Product })[];`

*"Ketambahan array `orderItems`. Isi array ini wujud dasarnya adalah tabel OrderItem murni, **DAN JUGA** di dalam setiap item tersebut ketambahan properti `product` yang wujudnya sama persis dengan tabel Product murni."*

Berkat parameter yang sangat panjang dan presisi ini, mesin TypeScript akan mengizinkan masuknya JSON raksasa berdarah yang kita lihat di Part 4 tadi tanpa mengeluarkan satu pun *error*.

### 1. Misteri `subtotal` vs `total` (Kenapa Dihitung Ulang?)

Kesalahpahaman di sini terletak pada definisi kata **Total**. Di dalam arsitektur *e-commerce*, ada dua jenis total yang nilainya sangat berbeda:

* **`total` (Grand Total):** Ini adalah uang keseluruhan yang harus dibayar pembeli. (Hasil dari fungsi `reduce` di atas, nilainya **350.000**).
* **`subtotal` (Row Total):** Ini adalah total harga untuk **satu jenis barang saja** (Harga Satuan × Jumlah Beli).

**Skenario Bencana jika kita memakai `total`:**
Bayangkan jika di dalam fungsi `map()` tadi Anda menuliskan: `subtotal: total`.
Maka wujud JSON yang dikirim ke *Frontend* akan hancur seperti ini:

```json
"items": [
  {
    "productName": "VGA RTX 4090",
    "price": 150000,
    "quantity": 2,
    "subtotal": 350000 // <--- SALAH! Seharusnya 300.000
  },
  {
    "productName": "Keyboard Mechanical",
    "price": 50000,
    "quantity": 1,
    "subtotal": 350000 // <--- SALAH! Seharusnya 50.000
  }
]

```

Jika *Frontend* merender ini di layar, pembeli akan jantungan karena melihat harga subtotal setiap baris barang membengkak menjadi 350.000!

Oleh karena itu, di dalam fungsi `map()` (yang tugasnya membedah barang *satu per satu*), kita **wajib** menghitung ulang khusus untuk baris barang tersebut (`item.price * item.quantity`), agar nilainya akurat per baris (300.000 untuk VGA, 50.000 untuk Keyboard).

### 2. Misteri Posisi Kurung `Number(...)` (Sihir Prisma Decimal)

Anda bertanya: *"Kenapa sintaksnya `Number(item.price) * item.quantity`, BUKAN `Number(item.price * item.quantity)`?"*

Ini adalah pertanyaan tingkat *Senior Developer*. Jawabannya berhubungan dengan **Hukum Urutan Eksekusi JavaScript** dan **Tipe Data Prisma**.

Di PostgreSQL dan Prisma, kolom harga (`price`) biasanya disimpan dengan tipe data `Decimal` (untuk mencegah uang hilang sepersekian sen akibat *bug* *floating point* di komputer).
Ketika Prisma menarik `item.price` dari *database*, wujudnya di Node.js **BUKAN** angka primitif JavaScript (seperti `150000`), melainkan sebuah **Objek Raksasa** (berasal dari pustaka `Decimal.js`).

Sementara itu, `item.quantity` adalah angka primitif murni (tipe data `number`).

**Mari kita simulasikan jika Anda memakai cara kedua: `Number(item.price * item.quantity)**`

Sesuai hukum matematika JavaScript, mesin akan mengeksekusi operasi di dalam kurung pembungkus terlebih dahulu:

1. Mesin mencoba mengeksekusi: `item.price * item.quantity`
2. Mesin melihat: `[Objek Decimal Raksasa] * [Angka Primitif 2]`
3. **BOM!** Mesin TypeScript langsung *Error* (atau di JavaScript murni akan menghasilkan `NaN` / *Not a Number*). Anda **tidak bisa** menggunakan operator bintang `*` secara langsung untuk mengalikan sebuah Objek dengan sebuah Angka primitif. Operasi gagal total sebelum sempat menyentuh fungsi `Number()`.

**Sekarang bandingkan dengan cara instruktur Anda: `Number(item.price) * item.quantity**`

1. Mesin mengeksekusi fungsi `Number(item.price)` terlebih dahulu.
2. Mesin berkata: *"Ubah Objek Decimal Raksasa ini menjadi Angka Primitif biasa!"*
3. Objek hancur, berubah menjadi angka primitif `150000`.
4. Barulah mesin mengeksekusi perkalian: `150000 * 2`.
5. Karena keduanya sudah sama-sama angka primitif, perkalian berjalan sangat mulus dan menghasilkan nilai akurat.

Itulah mengapa instruktur Anda harus "melebur" Objek Decimal tersebut menjadi angka biasa terlebih dahulu **sebelum** operator perkalian `*` boleh bekerja!
